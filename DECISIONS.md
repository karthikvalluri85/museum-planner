# Decisions

One line per architectural decision and why. Generated from `docs/decisions.json` by `node tools/gen-architecture.mjs`; edit the JSON, not this file. Entries marked (assumption) were made without the owner's input and should be confirmed.

- **D01 Ingestion is a Cloud Run job, not a service.** The ingester runs to completion and exits; it listens on no port. *Why:* Pulling a museum's API is a batch with a beginning and an end. A job is billed only while it works and cannot be reached from the internet at all.
- **D02 The planner is stateless.** A plan is a pure function of the request and the stored museum. Replanning is another POST /api/plan carrying the current gallery, the objects already seen, and the wings to skip; the browser holds that state. *Why:* No sessions means no session store, instances can scale to zero between visits, and any instance can answer any request.
- **D03 The planner serves the web frontend.** Static files ship inside the planner image and are served from /. *Why:* One deployable and one URL for the demo. Same origin, so no CORS. A separate frontend service would add a deploy step and nothing else.
- **D04 Firestore is the only shared state, behind a schema contract.** ingestion-job is the sole writer and planner has read-only IAM. The document shapes are contracts in contracts/firestore, and each side validates them with its own models. *Why:* The brief fixes the system at five pieces, so there is no data-API service between the two deployables. Treating the documents as a versioned contract with one writer gives the same decoupling without a sixth piece.
- **D05 Pub/Sub is pulled by the job; Cloud Scheduler starts the job (assumption).** Publishing {museum_id} to topic ingest-museum queues a museum. The job drains the pull subscription at the start of every execution. A Scheduler tick starts an execution every 10 minutes; deploy/add-museum.sh publishes and starts one immediately. *Why:* Pub/Sub push cannot start a Cloud Run job directly, and the usual bridge (Eventarc plus Workflows) would add two pieces. Pull-and-drain keeps the job a job and keeps adding a museum to one publish, at the cost of up to 10 minutes of delay.
- **D06 Objects are stored in chunk documents.** Up to 250 normalized objects per Firestore document under museums/{id}/object_chunks. *Why:* A planner cold start loads a whole museum. One document per object would cost about 1,500 reads per cold start and leave the free tier on launch day; chunks cost about 6.
- **D07 The museum document is written last.** An ingest run writes the floor graph, then the chunks, then deletes stale chunks, then the museum document, whose chunk_count is the pointer readers trust. *Why:* A run that fails halfway never leaves readers pointing at half-written data, without needing a transaction across hundreds of kilobytes.
- **D08 Objects without a gallery are dropped at ingestion.** The object schema requires a non-empty gallery, so an object the museum's API does not place in a gallery never reaches Firestore. *Why:* Never invent gallery numbers. Enforcing it at the data boundary means the planner cannot plan such an object even by mistake.
- **D09 The floor graph is hand-built, coarse, and says how far it has been verified.** One JSON graph per museum, bundled in the ingestion image. A node is a run of adjacent galleries on one level. The graph carries a verification status that every plan repeats in its notices. *Why:* No collection API describes which galleries connect or where the elevators are. A coarse graph can be built by hand in a day; saying plainly that it is unverified is the honest way to ship it.
- **D10 Unknown means not step-free.** An edge is step_free only when the published plan supports it. A connection we are unsure about is marked not step-free and given a name. *Why:* Wrongly saying no step-free route exists costs a visitor a suggestion. Wrongly saying one exists can strand them at a staircase.
- **D11 plan.step_free is computed, never echoed.** The planner derives step_free from the segments the plan actually uses and asserts invariants I1 and I2 before responding; on failure it returns an error rather than a plan. *Why:* The claim a wheelchair user relies on must not depend on the request flag being threaded through correctly.
- **D12 Greedy scoring and routing.** Score objects by interest and tag overlap weighted by the constraint profile, then repeatedly take the best feasible stop from the current position using shortest paths on the graph. *Why:* Good enough beats optimal for a visit of a dozen stops, it is easy to explain, and it is deterministic, so replanning never surprises.
- **D13 Why-sentences come from templates, not a language model.** Each sentence is assembled from the object's own tags and fields, and the response lists which fields were used. *Why:* Every claim must be grounded in the museum's data. Templates cannot hallucinate, cost nothing, and add no dependency.
- **D14 Services share contracts, not code.** Each deployable has its own models and tests them against /contracts. Nothing is imported across services. *Why:* Either side can be rewritten or redeployed alone, and `gcloud run deploy --source` uploads one directory at a time anyway.
- **D15 A file-backed store for offline tests.** Both deployables accept STORE_BACKEND=file, which reads and writes the same documents as JSON files in the Firestore layout. *Why:* The whole pipeline (ingest a fixture, then plan from it) can be tested with nothing but Python: no emulator, no Java, no Docker, no GCP.
- **D16 Contract tooling has zero dependencies.** tools/*.mjs validates the contracts, the floor graphs, and planner responses using only Node's standard library, including a small parser for the YAML subset the OpenAPI file uses. CI also runs openapi-spec-validator as an independent check. *Why:* The gate has to run on a machine where nothing can be installed. It tests itself (tools/selftest.mjs) so a green result means something.
- **D17 The planner is public and stores nothing about visitors.** Unauthenticated ingress, no accounts, no cookies, no request bodies logged, no secrets. *Why:* What a visitor's body can do is sensitive. The simplest way to protect it is never to keep it.
- **D18 Hard caps on scale (assumption).** Planner: 0 to 3 instances, concurrency 40. Job: one task, one retry, 30-minute timeout, 1,500 objects per museum. *Why:* A launch-day spike can slow the app down but cannot produce a surprising bill.
- **D19 Art Institute of Chicago is the second museum (assumption).** The second adapter targets the AIC API. *Why:* Its records carry a gallery title for works on view, which is the one field planning needs. Adding it shows the pipeline is not hardcoded to the Met.
- **D20 Python 3.12 and FastAPI, as specified.** No change of stack was proposed. *Why:* The brief's stack fits: the work is I/O and data shaping, the Google client libraries are first-class, and Pydantic gives runtime validation of every contract.
- **D21 Local-first, deploy later.** Everything is built and tested offline; deployment is a parameterized script and workflow that run once a GCP project and GitHub repository exist. *Why:* No cloud credentials were available during the build. Nothing in the repo claims to be deployed until a real request has been made against it.
